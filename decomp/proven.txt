# --- SOLVED: the vtable dispatches now carry their arguments ------------------

# --- 2026-08-25: MdtWorld RECOVERED, and it is not on UT2004's path -----------
#
# The first object out of the HANDOVER.md 11 item 2 group. FAIL -> ok, 10 errors
# to 0, and the build goes 109 -> 110 with every previously-compiling .o
# byte-identical and all eight gates unchanged.
#
# WHAT FIXED IT. ghidra_clean.collapse_outgoing_aggregate_copy, a pre-pass, not
# a repair-loop rule. gcc 3.2 passes an aggregate BY VALUE by copying it
# word-at-a-time into the outgoing argument area and then calling; Ghidra
# renders those ABI mechanics literally -- a pointer to a frame slot it does not
# declare, a copy loop, then the callee's argument rebuilt BYTE BY BYTE out of
# that slot into a kd_aggNN temporary. In C none of it is needed, because `f(x)`
# marshals `x` itself. So the whole sequence collapses to passing the source.
#
#   THE CHECK THAT MAKES IT SAFE is the size: the loop's own trip count times
#   its element width must equal the size of the aggregate parameter at the
#   call, taken from the prototype. 19 * 4 = 76 = MdtKeaParameters,
#   23 * 4 = 92 = MdtKeaConstraints. Anything else is refused, not rounded.

# --- 2026-08-25 (second session): THE VPTR STORE, AND keaLCPSolver ------------

# neighbour's EXTERNAL slot, so every virtual call in the function goes through

# --- 2026-08-25 (second session): THE LAST SIX ERRORS, DIAGNOSED --------------
#
# keaRbdCore_unified is 4 and keaLCP_new is 2. Both were opened far enough to
# say exactly what they need, and NEITHER was repaired, for different reasons.
#
# keaRbdCore_unified -- FOUR ERRORS, THREE COPY LOOPS, AND A PREREQUISITE THAT
# IS NOT A FRAME PROBLEM.
#
# All three `stack0x` sites are the outgoing by-value aggregate marshalling
# collapse_outgoing_aggregate_copy already solves for MdtWorld. Read straight
# off the shipped prologue:
#
#   4c: lea 0x60(%esp),%edi     ; outgoing slot
#   50: lea 0x70(%ebp),%esi     ; &parameters     (5th argument)
#   53: mov $0x13,%ecx          ; 19 words = 76 = MdtKeaParameters
#   58: rep movsl
#   5a: mov $0x17,%ebx          ; 23 words = 92 = MdtKeaConstraints
#   5f: lea 0x4(%esp),%edi      ; outgoing slot
#   65: lea 0x8(%ebp),%esi      ; &pconstraints   (1st argument)
#   68: rep movsl
#
# `register0x00000010` is entry-ESP, so the `+ 1` word the loop advances before
# its first read is ebp+8 -- `pconstraints`. That is the cdecl ABI, confirmed by
# `lea 0x8(%ebp),%esi` above, and it is what HANDOVER.md 11 item 2 already said.
#
# FOUR reasons the pass declines, and they are separable:
#
#   1. its call-site regex cannot cross a NEWLINE. Ghidra wraps
#      `keaFunctions__checkPrintDebugInput\n   (&vanillaFunctions,kVar1,kVar3,…)`
#      so the callee name and the argument list are on different lines and the
#      SIZE CHECK never runs. _trace_pointer_base had this same defect and it
#      was already fixed there. This alone blocks site 1, whose source
#      (`parameters`) traces correctly and whose 76 bytes are right.
#   2. MARSHAL_LOOP does not match the register0x00000010 shape: the source is
#      advanced in the for-header's COMMA operator
#      (`for (i = 0x17; src = src + 1, i != 0; …)`), the body is
#      `*dst = *src;` rather than `*dst = src->field;`, and the source
#      assignment carries a cast, which the `between` group disallows.
#   3. `register0x00000010` has to be NAMED as the first stack parameter.
#   4. AND THIS IS THE ONE THAT DECIDES IT. With 1-3 fixed the collapse would
#      emit `keaFunctions__checkPrintDebugInput(&vanillaFunctions, pconstraints,
#      parameters, …)` -- and gen_prelude declares that callee from
#      kd_protos10.h, i.e. with the `kd_agg92`/`kd_agg76` OPAQUE STAND-INS, so
#      passing an `MdtKeaConstraints` is "incompatible type for argument 2".
#
#      MdtWorld collapsed cleanly only because ITS callee,
#      MdtKeaAddConstraintForces, is declared by a PUBLIC HEADER with the real
#      types; the kd_aggNN prototype is used only to SIZE the parameter.
#      `keaFunctions::checkPrintDebugInput` is a C++ method with no public
#      declaration, so the stand-in is what the body sees.
#
# SO THE NEXT MOVE HERE IS NOT A FRAME REPAIR. It is gen_prelude declaring a
# mangled import with the REAL aggregate types. The stand-ins exist because
# kd_protos.h is flat and dependency-free FOR GHIDRA (HANDOVER.md 5); a prelude
# is compiled in a translation unit that already has kd_types.h and kd_karma.h
# and does not need them. Do that first, then 1-3, in that order.
#
# One more thing that changed under this: site 3's aggregate is passed through
# an INDIRECT vtable call (slot +0x14, `allocateMemory(keaTempMemory*,
# MdtKeaConstraints, int)`), so _proto_param_size cannot size it by name -- but
# vtable_slots.slot_table now can, because fix_vptr_store made the slot

# keaLCP_new -- TWO ERRORS, AND NAMING THEM WOULD BE ACTIVELY HARMFUL.
#
# HANDOVER.md 13 says "do not text-repair this frame". That is right, and the
# reason is worth more than the instruction. The function declares
#
#     uint auStack_3c [3];                                  /* 12 bytes */
#     uVar6 = this->n * 4 + 0xfU & 0xfffffff0;              /* a RUNTIME size */
#     I        = (int *)((int)auStack_3c - uVar6);
#     C        = (int *)((int)auStack_3c + uVar6 * -2);
#     clamped  = (int *)((int)auStack_3c + uVar6 * -5);
#     unclamped= (int *)((int)auStack_3c + uVar6 * -6);
#
# -- six alloca-sized regions BELOW a twelve-byte local. The original allocas
# them (gcc merged six `sub %esp` into one) and Ghidra re-based the whole area
# on whichever local landed at its top. `&stack0xffffffb4 + uVar6 * -6` is an
# outgoing argument slot in that same shifted area.
#
# Naming those two slots would take the object from 2 errors to 0 and hand the
# build a function that writes 6*(4n+15 & ~15) bytes below a 12-byte array. That
# is the trade materialise_alloca_frame's docstring already warns about in the
# other direction -- "it COMPILED, passed the substitute gate, and then
# segfaulted on its first call in a real match". The compile error is the useful
# signal, exactly as for MeSimpleFile_linux.
#
# THE REPAIR IS materialise_alloca_frame, EXTENDED, not a frame naming. It
# handles `dest = (T)(&stack0xHHHH + negVar)` with `negVar = -(EXPR*K + 15 &
# ~15)`; this is the MULTI-REGION form of the same idiom -- one positive size in
# `uVar6` and six regions at multiples of it, based off a named local rather
# than a `stack0x`. The multipliers {1,2,3,5,6} are in the text and the size
# expression is the same `+ 0xf & 0xfffffff0` the existing rule already reads.

# --- 2026-08-25 (second session): keaLCP_new's FRAME, READ OFF THE PROLOGUE ---
#
# Recorded so MOVE 2 is a mechanical job and not a research one. NOT repaired:
# this is a frame RECONSTRUCTION, which is the class dead end 20 refutes, and it
# should be done by extending materialise_alloca_frame rather than by naming
# slots. What follows is every fact that extension needs.
#
# THE SHIPPED PROLOGUE. `keaLCPSolver::solveLCP` allocas SIX regions of the same
# runtime size and then a fixed twelve-byte outgoing argument area:
#
#   28f: sub %edi,%esp ; mov %esp,-0x20(%ebp)      alloca #1
#   294: sub %edi,%esp ; mov %esp,-0x24(%ebp)      alloca #2
#   299: sub %edi,%esp ; mov %esp,%esi             alloca #3
#   29d: sub %edi,%esp ; mov %esp,%ebx             alloca #4
#   2a1: sub %edi,%esp ; mov %esp,-0x28(%ebp)      alloca #5
#   2a6: sub %edi,%esp ; mov %esp,-0x2c(%ebp)      alloca #6
#   2ab: sub $0xc,%esp                             outgoing arguments
#
# with `%edi` = `uVar6` = `this->n * 4 + 0xf & 0xfffffff0` -- the SAME
# `+ 0xf & 0xfffffff0` rounding materialise_alloca_frame already reads, only
# positive and used six times instead of negated once.
#
# WHAT GHIDRA DID WITH IT. It re-based the whole region on `auStack_3c`, the
# local that happens to sit at its top, and expressed every address as a fixed
# frame offset plus a runtime shift. From <object>.locals (offsets are
# entry-ESP relative; ebp offset = these + 4):
#
#   auStack_3c   -60  (ffffffc4)  uint[3]   the pre-sub %esp -- the base
#   pMStack_44   -68  (ffffffbc)  MeReal *  outgoing argument slot 2
#   stack0xffffffb8  -72                    outgoing argument slot 1
#   stack0xffffffb4  -76                    outgoing argument slot 0
#   iStackY_50   -80  (ffffffb0)  int       where the CALL pushes its return
#                                           address -- `iStackY_50 = 0x1025b;`
#                                           is that, not a variable
#
# SO THE LAYOUT IS FULLY DETERMINED, and none of it is a guess:
#
#   base       = alloca(6 * uVar6 + 12)      /* lowest address */
#   outgoing   = base            + {0,4,8}   /* &stack0xffffffb4 + uVar6*-6 */
#   region k   = base + 12 + (6-k)*uVar6     /* k = 1..6 */
#   auStack_3c = base + 12 + 6*uVar6         /* what Ghidra bases its
#                                               arithmetic on */
#
# and the recovered body's `I`, `C`, `clamped`, `unclamped` are regions 1, 2, 5
# and 6, which is what `(int)auStack_3c - uVar6`, `+ uVar6 * -2`, `* -5` and
# `* -6` already say.
#
# WHY NAMING THE TWO `stack0x` SLOTS INSTEAD WOULD BE WORSE THAN THE ERRORS.
# `auStack_3c` is declared `uint[3]` -- TWELVE BYTES. Without the alloca, every
# one of those addresses is below a twelve-byte local, so the object would
# compile and then read and write `6*(4n+15 & ~15)` bytes of somebody else's
# stack. materialise_alloca_frame's own docstring records what that costs: "it
# COMPILED, passed the substitute gate, and then segfaulted on its first call in
# a real match". Until the alloca is materialised the compile error is the
# useful signal.
